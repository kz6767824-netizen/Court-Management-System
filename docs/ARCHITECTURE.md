# e-Judiciary — Architecture & Contract (source of truth for code)

Project: e-Judiciary: Automated Court Case & Hearing Management System (CS3004 SDA, FAST Islamabad).
Design sources: Deliverable 2 (proposal), 3 (12 fully dressed use cases UC-01..UC-12),
4 (domain model + SSDs), 5 (design class diagram + sequence diagrams).
If documents disagree, the Deliverable 5 design class diagram wins. Use cases define behaviour.

## 1. Stack (decided)
- Backend: Java 17, Maven, Spring Boot 3.3.x (web, validation, data-jpa, security), Flyway
- Auth: Spring Security, stateless JWT, BCrypt password hashes
- DB: H2 (file mode) for `dev` and tests, PostgreSQL for `prod`. SQL must run on both (plain ANSI only)
- Frontend: React + Vite + TypeScript in /frontend, talks to backend via REST/JSON
- Tests: JUnit 5, Spring Boot Test, MockMvc
- Deploy (last wave): backend on Railway/Render (Dockerfile only if the host requires it), Postgres on Neon/Supabase, frontend on Vercel. Docker is not needed for local development.

Note: the proposal said Swing/JavaFX + Oracle. We use web + Postgres so it can be deployed. The layered
design (controller → service → repository → DB) from Deliverable 5 is kept unchanged.

```
  config/    SecurityConfig, CorsConfig, JwtProperties

  history/   CaseHistoryService  (shared; owned by c2)
  auth/      controller, service, dto            (UC-01)
  user/      controller, service, repository, dto (UC-12)
  assignment/ ...                                 (UC-04)
  cases/     ...                                  (UC-02, 03, 05)
  hearing/   ...                                  (UC-06, 07, 09)
  causelist/ ...                                  (UC-08)
  view/      ...                                  (UC-10, 11)
```
Each slice: `XController` (HTTP only) → `XService` (business rules, transactions) → `XRepository`.
Controllers never touch repositories. Entities never leave the service layer; controllers use DTOs (records).
Controllers named in Deliverable 5: UserController, CaseController, HearingController — keep those names.

## 3. Database schema (Flyway V1__schema.sql — created by c2, columns below are fixed)
```sql
CREATE TABLE user_account (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  username VARCHAR(50) NOT NULL UNIQUE,
  password_hash VARCHAR(100) NOT NULL,
  display_name VARCHAR(100) NOT NULL,
  contact_no VARCHAR(30),
  role VARCHAR(20) NOT NULL,              -- ADMIN, CLERK, JUDGE, LAWYER, LITIGANT
  is_active BOOLEAN NOT NULL DEFAULT TRUE
);
CREATE TABLE admin_profile   (user_id BIGINT PRIMARY KEY REFERENCES user_account(id), admin_id VARCHAR(30) NOT NULL UNIQUE);
CREATE TABLE clerk_profile   (user_id BIGINT PRIMARY KEY REFERENCES user_account(id), employee_id VARCHAR(30) NOT NULL UNIQUE);
CREATE TABLE judge_profile   (user_id BIGINT PRIMARY KEY REFERENCES user_account(id), judge_number VARCHAR(30) NOT NULL UNIQUE, designation VARCHAR(80), courtroom_no VARCHAR(20));
CREATE TABLE lawyer_profile  (user_id BIGINT PRIMARY KEY REFERENCES user_account(id), bar_number VARCHAR(30) NOT NULL UNIQUE, contact_number VARCHAR(30), chamber_address VARCHAR(200));
CREATE TABLE litigant_profile(user_id BIGINT PRIMARY KEY REFERENCES user_account(id), litigant_number VARCHAR(30) NOT NULL UNIQUE, national_id VARCHAR(20) NOT NULL UNIQUE, address VARCHAR(200));

CREATE TABLE court_case (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  case_number VARCHAR(30) NOT NULL UNIQUE,            -- server generated: CASE-2026-0001
  case_type VARCHAR(40) NOT NULL,                     -- CIVIL, CRIMINAL, FAMILY, ...
  title VARCHAR(200) NOT NULL,
  description VARCHAR(2000),
  filing_date DATE NOT NULL,
  current_status VARCHAR(30) NOT NULL,                -- see §5
  registered_by BIGINT NOT NULL REFERENCES user_account(id)
);
CREATE TABLE case_party (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  case_id BIGINT NOT NULL REFERENCES court_case(id),
  litigant_id BIGINT NOT NULL REFERENCES user_account(id),
  party_role VARCHAR(15) NOT NULL,                    -- PLAINTIFF, DEFENDANT
  joined_on DATE NOT NULL,
  UNIQUE (case_id, litigant_id)
);
CREATE TABLE judge_assignment (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  case_id BIGINT NOT NULL REFERENCES court_case(id),
  judge_id BIGINT NOT NULL REFERENCES user_account(id),
  assigned_on DATE NOT NULL,
  ended_on DATE                                       -- NULL = current judge
);
CREATE TABLE legal_representation (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  case_party_id BIGINT NOT NULL REFERENCES case_party(id),
  lawyer_id BIGINT NOT NULL REFERENCES user_account(id),
  starts_on DATE NOT NULL,
  ends_on DATE                                        -- NULL = current counsel
);
CREATE TABLE hearing (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  hearing_number VARCHAR(30) NOT NULL UNIQUE,         -- HRG-2026-0001
  case_id BIGINT NOT NULL REFERENCES court_case(id),
  judge_id BIGINT NOT NULL REFERENCES user_account(id),   -- copied from current assignment
  scheduled_at TIMESTAMP,                             -- NULL when ADJOURNED without a new date
  venue VARCHAR(60),
  status VARCHAR(15) NOT NULL,                        -- PENDING, SCHEDULED, ADJOURNED, COMPLETED
  UNIQUE (judge_id, scheduled_at)                     -- DB-level double-booking guard (NULLs allowed many times)
);
CREATE TABLE hearing_outcome (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  hearing_id BIGINT NOT NULL UNIQUE REFERENCES hearing(id),
  recorded_at TIMESTAMP NOT NULL,
  outcome_type VARCHAR(40) NOT NULL,                  -- NEXT_DATE_GIVEN, JUDGMENT_RESERVED, DISPOSED, ...
  details VARCHAR(2000)
);
CREATE TABLE case_history_entry (                     -- append-only, never UPDATE/DELETE
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  case_id BIGINT NOT NULL REFERENCES court_case(id),
  occurred_at TIMESTAMP NOT NULL,
  event_type VARCHAR(30) NOT NULL,                    -- REGISTRATION, STATUS_UPDATE, HEARING_PROPOSED, HEARING_SCHEDULED, HEARING_RESCHEDULED, HEARING_ADJOURNED, OUTCOME_RECORDED, JUDGE_ASSIGNED, COUNSEL_ASSIGNED
  description VARCHAR(500) NOT NULL,
  resulting_status VARCHAR(30),
  performed_by BIGINT REFERENCES user_account(id)
);
CREATE TABLE cause_list (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  list_number VARCHAR(30) NOT NULL UNIQUE,
  hearing_date DATE NOT NULL,
  generated_at TIMESTAMP NOT NULL,
  published BOOLEAN NOT NULL DEFAULT FALSE
);
CREATE TABLE cause_list_entry (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  cause_list_id BIGINT NOT NULL REFERENCES cause_list(id),
  hearing_id BIGINT NOT NULL REFERENCES hearing(id),
  sequence_number INT NOT NULL
);
```
Flyway version ranges (avoid collisions): c2 V1–V9, k1 V10–V19, c3 V20–V39 (seed data is V30), spare V40+.
Never edit a merged migration; add a new one.

## 4. API contract (JSON, base path /api, JWT in `Authorization: Bearer <token>`)
Roles: ADMIN, CLERK, JUDGE, LAWYER, LITIGANT. Errors: HTTP 4xx/5xx with
`{ "timestamp", "status", "error", "message", "details": [..] }`. 401 not logged in, 403 wrong role/not your case,
404 missing, 409 business conflict (double-booking, invalid transition), 422/400 validation.

| UC | Method + path | Who | Notes |
|---|---|---|---|
| 01 | POST /api/auth/login `{username,password,role}` → `{token,userId,displayName,role}` | public | 401 if bad creds or role ≠ account role; inactive user denied |
| 01 | GET /api/auth/me | any | current user + role |
| 12 | GET /api/users?role= · POST /api/users · PUT /api/users/{id} · PATCH /api/users/{id}/role · PATCH /api/users/{id}/deactivate | ADMIN | create takes role-specific profile fields |
| 12/04 | GET /api/lookup/{judges\|lawyers\|litigants} | ADMIN, CLERK | id + name + number, for dropdowns |
| 02 | POST /api/cases `{caseType,title,description,filingDate,parties:[{litigantId,partyRole,lawyerId?}]}` → case incl. `caseNumber` | CLERK | needs ≥1 PLAINTIFF and ≥1 DEFENDANT; writes REGISTRATION history; initial status FILED |
| 03 | GET /api/cases?caseNumber=&caseType=&status=&party=&from=&to= | any | results scoped by role (§6) |
| 03 | GET /api/cases/{id} | any | 403 if not in scope |
| 05 | GET /api/cases/{id}/allowed-transitions · PATCH /api/cases/{id}/status `{newStatus,reason}` | CLERK, JUDGE(assigned) | 409 on invalid transition; writes STATUS_UPDATE history |
| 04 | POST /api/cases/{id}/assignments/judge `{judgeId}` · POST /api/cases/{id}/assignments/counsel `{casePartyId,lawyerId}` | ADMIN | ends previous judge assignment (ended_on) |
| 06 | GET /api/hearings/available-slots?caseId=&from=&to= · POST /api/hearings `{caseId,scheduledAt,venue}` → PENDING | CLERK | 409 if judge slot taken |
| 06 | GET /api/hearings/pending · POST /api/hearings/{id}/approve | JUDGE (own cases) | PENDING → SCHEDULED, history entry |
| 07 | PATCH /api/hearings/{id}/reschedule `{newDateTime,reason}` · PATCH /api/hearings/{id}/adjourn `{reason}` | CLERK | reschedule keeps SCHEDULED; adjourn → ADJOURNED + scheduled_at NULL; history keeps old date |
| 09 | POST /api/hearings/{id}/outcome `{outcomeType,details}` | JUDGE (own cases) | hearing → COMPLETED; OUTCOME_RECORDED history; one outcome per hearing |
| 08 | POST /api/cause-lists `{date}` → unpublished preview · POST /api/cause-lists/{id}/publish · GET /api/cause-lists?date= | CLERK create/publish; any role reads published | entries = SCHEDULED hearings on that date, ordered by time; empty list is valid |
| 10 | GET /api/cases/{id}/progress | LAWYER, LITIGANT (also JUDGE, CLERK, ADMIN) | status, hearings, outcomes, judge, counsel, history; read-only |
| 10/11 | GET /api/me/cases | any | each row: caseNumber, parties, caseType, nextHearing, status |

## 5. Business rules (shared constants live in `common/rules`, pure Java + unit tests)
- Case status: `FILED → IN_PROGRESS → JUDGMENT_RESERVED → DISPOSED → CLOSED`; also `IN_PROGRESS → DISPOSED`. Nothing else is legal.
- Hearing status: `PENDING → SCHEDULED → COMPLETED`; `SCHEDULED → ADJOURNED → SCHEDULED` (via reschedule); PENDING cannot be adjourned.
- Slots: 30-minute slots, 09:00–16:00, Monday–Friday, not in the past. Configurable in application.yml.
- Double-booking: a judge cannot have two hearings (PENDING or SCHEDULED) at the same `scheduled_at`. Enforced in service (409) and by the DB unique constraint.
- Hearing `judge_id` = the case's current judge assignment. A case with no judge cannot get a hearing (409).
- Every status change, hearing event, assignment and outcome writes a `case_history_entry` in the SAME transaction. History is append-only.
- IDs shown to users are `case_number` / `hearing_number` (generated server side, sequential per year).

## 6. Access scoping (UC-03, 10, 11) — enforced in services, not only in the UI
- ADMIN, CLERK: all cases. JUDGE: cases where they hold the current judge assignment. LAWYER: cases where they currently represent a party.
- LITIGANT: cases where they are a party. Anything else → 403 (detail endpoints) or filtered out (list endpoints).

## 7. Conventions
- Passwords: BCrypt. Never log or return `password_hash`. Dev seed password for all demo users: `Password123!` (dev profile only).
- DTOs are Java records with Bean Validation annotations. Dates ISO-8601. Times in server local timezone (Asia/Karachi) for simplicity.
- Each use case gets: service tests (rules) + MockMvc test (happy path + each Extension from Deliverable 3 that applies).
- Code comments reference the use case, e.g. `// UC-06 step 8`. Keeps the SDA traceability story easy for the report.
- Frontend is sliced the same way: `frontend/src/features/<module>/`; shared API client in `src/api/`, auth in `src/auth/`.
